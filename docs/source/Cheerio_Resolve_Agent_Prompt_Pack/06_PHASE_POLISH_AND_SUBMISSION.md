# Phase 06 — UI Polish, Assignment Artifacts, and Demo

## Goal
Polish the working flow without breaking state behavior, then prepare the assignment deliverables.

## UI polish checklist
- Consistent type scale, spacing, surfaces, borders, and button hierarchy.
- Clear issue/status context from S1 through S5.
- Visible mock-data and simulation labels.
- Accessible contrast, keyboard focus, and semantic labels.
- Responsive desktop and narrow layout.
- No unnecessary dashboard, onboarding questionnaire, or bot.
- Loading/error/pending/success states match actual state machine.
- Animation is minimal and respects reduced-motion settings.

## Required evidence/screenshots
Capture:
1. S2 diagnosis;
2. S3 before/after confirmation;
3. S4 pending or failed-verification state;
4. S5 handoff case file.

Use the actual running prototype and do not composite fake status into screenshots.

## Assignment deliverables
1. Four-page maximum submission draft, in the author's voice.
2. Clickable prototype link or exact run instructions.
3. Four screenshots above.
4. Architecture/data-flow diagram.
5. Cost spreadsheet with assumptions and dated sources.
6. Honest AI chat log, including corrections and mistakes.
7. Optional 3–5 minute Loom plan/recording.

## Four-page structure
1. Problem, persona, evidence labels, top-five issue hypotheses.
2. Alternatives, prioritization, selected scope, rejected alternatives, “won't do.”
3. End-to-end flow, architecture, safety, human handoff, prototype screenshots.
4. Metrics, baseline plan, provisional target, cost/economics assumptions, next steps.

## Cost sheet
Include assumptions, monthly volume, issue mix, eligible cases, resolution rate, human cost, model/provider pricing, tokens, hosting, cost/query, savings/break-even, billing options, margin, decision-layer comparison (rules, standard LLM, Laya; Jev only if access is available), and audit thresholds. Every unmeasured value is an assumption. Source prices with access date.

## Loom narrative (3–5 minutes)
1. State the user problem and promise.
2. Show the rejected template and contextual entry.
3. Show diagnosis and evidence.
4. Show before/after and confirmation.
5. Show pending or failed verification honestly.
6. Show the handoff case file.
7. Explain the safety boundary and what is mocked.
8. Close with the metric and what would be validated with real ticket data.

## Acceptance gate
The visual polish improves comprehension, not just appearance. All screenshots reflect the actual app state. Deliverables agree with one another and distinguish prototype behavior from production capability.
